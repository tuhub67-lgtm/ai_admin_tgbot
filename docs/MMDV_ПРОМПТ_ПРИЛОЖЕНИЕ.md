## Контекст для Claude Code

Строим MVP продукта «Подхват AI+»: ИИ-администратор для частной стоматологической клиники. Клиника теряет пациентов на пропущенных звонках. Наш ИИ (имя — Анна) перехватывает обращение, ведёт диалог, доводит до записи. Владелец клиники видит карточки лидов и деньги в собственном приложении (PWA, позже — упаковка в RuStore).

Работай пошагово: (1) выведи план файлов и модулей, (2) реализуй по фазам ниже по порядку, (3) прогони приёмочные тесты, (4) выведи инструкцию деплоя. Стек: Python 3.12 backend (FastAPI + aiogram 3 + aiosqlite + GigaChat API), фронтенд — **vanilla JS + CSS, без сборщика** (осознанный выбор: ноль конфигурации, максимальная скорость MVP, готово к упаковке в TWA для RuStore без переделок). Один Chart.js с CDN — единственная внешняя зависимость фронтенда.

## Фаза 2 — Backend-ядро

Модули в `backend/`:

**`config.py`** — конфиг клиники в YAML на `clinic_id`: название, часы работы, шаг слотов (30 мин), прайс-диапазоны по услугам, средний чек, тексты Анны, chat_id Штаба в Telegram.

**`dialog_engine.py`** — диалог через GigaChat. Системный промпт Анны:
«Ты — Анна, администратор стоматологической клиники {название}. Тон: тёплый, краткий, без перегруза смайлами. Приоритеты: (1) понять запрос; (2) при острой боли — флаг СРОЧНО, предложить ближайшее окно; (3) предложить 2–3 конкретных слота; (4) собрать имя, подтвердить телефон; (5) вопросы цен — только диапазоны из прайс-конфига, точную стоимость называет врач на осмотре. Если пациент просит перезвонить или не хочет переписываться — зафиксируй это и пообещай звонок администратора в рабочее время (флаг `wants_callback`). НИКОГДА: не ставить диагнозы, не обещать результат лечения, не выдумывать услуги вне прайса, не давать скидок и особых условий даже если пациент настаивает или требует (такие просьбы — вежливо переадресовать администратору), не запрашивать медицинские подробности сверх повода обращения. Агрессия или запрос вне компетенции — вежливая эскалация человеку.»

**`qualifier.py`** — извлекает из диалога JSON: имя, телефон, услуга, желаемое время, срочность.

**`scheduler_lite.py`** — слоты из конфига клиники (рабочие часы, занятые — вручную через кабинет). Без интеграции с МИС на этом этапе. Ручной режим по умолчанию: Анна не бронирует слот жёстко, а создаёт заявку `pending` на желаемое время; администратор подтверждает тапом «Подтвердить», и только тогда пациенту уходит финальное подтверждение. Это исключает двойную бронь и даёт администратору контроль.

**`channels/`** — единый интерфейс `ChannelAdapter` (метод `send(phone_or_chat_id, text, buttons=None)`), три реализации:
- `channel_telegram.py` — aiogram, стандартно.
- `channel_max.py` — MAX Bot API (dev.max.ru): кнопка `request_contact` для получения номера, отправка сообщений; если у MAX Bot API нет прямой отправки первым по номеру — оставь заглушку `send_by_phone()` с TODO и комментарием «требует бизнес-аккаунт MAX с номерными уведомлениями, подключить когда будет верификация организации».
- `channel_sms.py` — через агрегатор (SMS.ru), только как fallback и как мост, НЕ как чат: первое сообщение содержит короткий текст + ссылку «продолжить в Telegram/MAX» + вариант «или мы перезвоним». Полный диалог в SMS не ведём (дорого, ответы плохо маршрутизируются).
- `dispatcher.py` — каскад: пробуем MAX → нет доставки за 30 сек → SMS. Telegram — если у клиента уже есть диалог в TG.

**`webhook_telephony.py`** — FastAPI-эндпоинт, принимает вебхук Novofon о пропущенном звонке (номер, время). В URL вебхука обязателен `clinic_token` (иначе сервер не знает, чья клиника) — валидировать его и резолвить в `clinic_id`. Триггерит `dispatcher.send()` с первым сообщением Анны в течение 30 секунд.

**`card_builder.py` + `shtab_bot.py`** — карточка лида дублируется в Telegram-группу Штаба (быстрый fallback-канал, пока владелец не привык жить в приложении): имя / телефон / услуга / время / срочность / источник / резюме диалога (3 строки, без медицинских деталей). Кнопки: «Подтвердить запись» (для `pending` из ручного режима — по тапу пациенту уходит финальное подтверждение), «Записан ✅ / Перезвонить / Потерян». При флаге `wants_callback` карточка помечена «просит звонок». Команда `/week` — отчёт: обращений, перехвачено, записано, оценка возвращённой выручки.

**Реалтайм-реакции, защита от спама, надёжность** (добавки к ядру):
- Redaction-фильтр: перед записью resume/transcript в БД — вычищать паттерны диагнозов и чувствительных фраз на `[скрыто]`.
- Дневной лимит: не более 1 авто-сообщения на номер телефона за 24 часа (поверх 15-минутного батчинга ниже).
- Поле `lead.recovered_from_miss` (bool): true, если первый контакт не привёл к записи, а повторный — привёл.
- Поле `delivery_status` на каждую попытку контакта (канал, success/fail).
- Статус лида → «Записан»: сообщение в Штаб отдельно от карточки: `✅ {имя} записан(а) — {услуга}, {время}\nВернули ≈ {сумма} ₽` (сумма = средний чек услуги; если `recovered_from_miss` — «Спасено» вместо «Вернули»). Батч, если 2+ события за 15 минут. Первая запись клиники за всё время — расширенный тёплый текст.
- Флаг СРОЧНО — отдельное немедленное сообщение, без денежной строки: `⚠️ Срочно: {имя}, {повод}, ждёт {N} мин`.
- НЕ слать реалтайм-уведомления по потерям/неответам — только в недельном отчёте. Cha-ching — только в Штаб (TG/MAX), не веб-пуш.

**`report_weekly.py`** — cron (планировщик): понедельник 09:00 МСК автоматически шлёт владельцу в личку недельный отчёт (обращений, перехвачено, записано, возвращено ₽, потери за неделю). `/week` остаётся как ручная команда по запросу. Без авто-отчёта ценность приходит, только если владелец сам вспомнит спросить.

**`api.py`** — REST-эндпоинты для фронтенда: `GET /api/leads` (лента карточек), `GET /api/leads/{id}/transcript` (редактированная полная расшифровка — для разворачивания в карточке), `POST /api/leads/{id}/status`, `POST /api/leads/{id}/confirm` (подтверждение `pending`-заявки из ручного режима → финальное сообщение пациенту, идемпотентно), `GET /api/money/weekly`, `GET /api/reliability-streak` → `{current_streak_days, record_days, last_incident: {date, resolved_in_minutes} | null}` (streak = дни подряд без лида, где ВСЕ каналы дали fail), `GET/POST /api/settings`, `POST /api/auth/magic-link`, `GET /api/auth/verify`.

Все данные — только на этом VPS (152-ФЗ). В карточках и логах — без диагнозов.

## Фаза 3 — PWA-кабинет владельца

`static/` — статический фронтенд, отдаёт FastAPI. Файлы: `index.html`, `app.js`, `tokens.css` (из Фазы 1), `styles.css`, `manifest.json`, `sw.js`.

**Авторизация — passwordless magic link, основной канал: Telegram/MAX Штаб-бот** (не email). Владелец пишет боту `/login` → бот присылает ссылку `https://{домен}/auth?token=...` прямо в мессенджер (живёт 15 минут, одноразовая) → переход выставляет JWT-сессию (привязан к `clinic_id`) в `localStorage`. Мессенджер — потому что почтовая доставка в РФ ненадёжна (спам-фильтры Яндекс/Mail.ru, корпоративные политики — подтверждено ресёрчем). Email-ссылка — только fallback, с собственного домена-отправителя, с пометкой «проверьте спам». На пилоте self-service регистрации НЕТ: новый клиент оставляет заявку на сайте, основатель подключает вручную и выдаёт доступ. Согласие на обработку ПДн (152-ФЗ) фиксируется при первом входе.

**Экран «Сегодня»** — лента карточек лидов (переиспользует тот же формат, что и в Штабе), фильтр по статусу, срочные — красным маркером сверху. По тапу на карточке разворачивается полный текст разговора (`GET /api/leads/{id}/transcript`, уже редактированный).

**Экран «Деньги»** — главная денежная цифра недели (`.money-figure`), график по дням (Chart.js), строка «пилот окупился на день N» — считается по формуле: сумма чеков записанных пациентов минус стоимость подписки/пилота. Под цифрой — счётчик надёжности из `/api/reliability-streak`: «{N} дней подряд — каждое обращение получило ответ», мельче — «Рекорд: {M} дней». Если есть `last_incident` — вместо счётчика короткая карточка: «Был сбой доставки {N} сообщения ({дата}) — устранили за {X} мин, дозвон обеспечили вручную. Новый отсчёт начат.»

**Экран «Настройки»** — часы работы, прайс-диапазоны, тексты Анны, переключатель каналов (MAX/Telegram/SMS).

**manifest.json + sw.js** — installable PWA, офлайн-кэш последнего отчёта. Без web-push на этом этапе (опционально, можно пропустить ради скорости).

## Фаза 4 — Онбординг-мастер (первый запуск)

Отдельный флоу `static/onboarding.html`, 4 шага, каждый 3–4 минуты, без техподдержки:

1. **Телефония** — развилка «какой у вас телефон?»: (а) умная АТС (Novofon/Mango/UIS) → показать URL вебхука с `clinic_token` и куда его вставить; (б) обычный/мобильный номер → инструкция условной переадресации по неответу (короткий USSD/код набирается на телефоне за минуту, с картинками). Половина малых клиник не имеет АТС — без ветки (б) они застревают на первом шаге.
2. **Расписание** — три варианта на выбор: «вручную через приложение» (по умолчанию, работает сразу) / «Google Sheets» (вставить ссылку на таблицу-шаблон) / «YClients» (поле под токен, помечено «скоро»).
3. **Прайс и тексты Анны** — готовые пресеты по 5 частым услугам стоматологии, можно отредактировать.
4. **Тестовый прогон** — кнопка «Позвонить самому себе»: приложение симулирует пропущенный звонок и показывает живой диалог Анны прямо на экране — владелец видит результат до подписки.

Критерий приёмки: полный проход без единой подсказки извне.

## Фаза 7 — Безопасность (обязательно, не опционально)

Реализуй с самого начала, а не «потом». Это медицинский контекст и российское право (152-ФЗ) — цена ошибки высокая.

**Секреты и ключи.** Все ключи (GigaChat, Novofon, MAX, SMS.ru, JWT-secret, DB) — только в `.env`, никогда в коде и не в git (`.gitignore` на `.env`). В репозитории — лишь `.env.example` с пустыми значениями. JWT-secret — длинная случайная строка, генерируется при деплое.

**Мультитенантность — изоляция клиник.** Каждый запрос к API и каждая запись в БД привязаны к `clinic_id` из JWT. НИКОГДА не отдавать данные одной клиники по токену другой: на каждом эндпоинте проверять, что `clinic_id` из токена совпадает с запрашиваемым ресурсом. Это критично: утечка карточек пациентов между клиниками — провал и юридический, и репутационный.

**Валидация входящего.** Вебхук телефонии: проверять `clinic_token` + по возможности подпись/IP Novofon (иначе злоумышленник шлёт фейковые «пропущенные» и жжёт наш баланс SMS). Все входящие тексты (диалог, настройки, формы) — валидировать и экранировать перед записью в БД и перед показом в кабинете (защита от инъекций и XSS в карточках).

**Аутентификация кабинета.** Magic-link токен: одноразовый, живёт 15 минут, привязан к `clinic_id`, после использования инвалидируется. JWT сессии — с разумным сроком (например 30 дней) и возможностью отзыва. Никаких паролей в MVP (меньше поверхность атаки).

**Защита от перерасхода (это и безопасность, и деньги).** Rate-limit на: вебхук телефонии (N событий/мин с номера), исходящие SMS (дневной лимит на клинику — иначе баг или атака сожжёт баланс), запросы к GigaChat (лимит на диалог, чтобы зациклившийся диалог не стоил состояние). При достижении лимитов — стоп + запись в лог + уведомление админа (тебя), не молчаливый отказ.

**Персональные данные (152-ФЗ).** Все ПДн (номера, имена пациентов) — только на российском VPS, не покидают его, не уходят в сторонние сервисы кроме необходимых (GigaChat — российский; телефония/SMS — российские). Redaction медданных (Фаза 2) применяется ДО записи в БД. Логи не содержат полных номеров карт и медицинских деталей. В `privacy.html` честно перечислить, что собираем и зачем.

**Транспорт.** Только HTTPS (Caddy автоматически, Let's Encrypt). HTTP → редирект на HTTPS. Куки/токены — с флагами Secure и HttpOnly где применимо.

**Тесты безопасности** (добавь в приёмочные): (a) запрос данных клиники A с токеном клиники B → отказ 403; (b) вебхук без валидного `clinic_token` → отказ; (c) превышение SMS-лимита → блок и уведомление, не безмолвный слив баланса; (d) протухший/использованный magic-link → отказ.

## Фаза 8 — Где вероятны баги: предупреждения для реализации

По каждому пункту — где риск и как действовать. Не игнорируй, это карта самых частых провалов именно этого класса приложений.

**Асинхронность и гонки.** aiogram и FastAPI — async. Риск: гонки при одновременных апдейтах статуса лида (два тапа «Записан» подряд), двойная отправка сообщения. Решение: идемпотентность операций смены статуса (повторный тап не создаёт второе событие/сообщение), блокировки на уровне записи лида.

**Внешние API падают и тормозят.** GigaChat, Novofon, MAX, SMS.ru — любой может ответить ошибкой, таймаутом или лимитом. Никогда не считать вызов успешным по умолчанию. Каждый внешний вызов: таймаут + ретрай с backoff (1–2 попытки) + graceful fallback (для доставки — каскад в следующий канал; для GigaChat — вежливое «администратор свяжется с вами» и эскалация). Ошибки логировать, не глотать.

**Токен-лимиты и стоимость GigaChat.** Длинный диалог раздувает контекст → растёт цена и латентность. Решение: ограничить историю диалога (последние N сообщений), жёсткий предел длины разговора, после — эскалация человеку. Зациклившийся диалог («не понял» по кругу) — детектить и эскалировать.

**Часовые пояса.** Классический источник багов в записи. Везде фиксировать МСК (или хранить UTC и конвертировать в МСК на выводе), единообразно. Тест «ночной запрос 02:00» специально это проверяет. Слоты, cron отчёта, «ждёт N минут» — всё в одной зоне.

**Парсинг ответа GigaChat в структуру.** `qualifier.py` ждёт JSON, модель иногда вернёт текст с преамбулой или кривой JSON. Решение: строго просить только JSON, оборачивать парсинг в try/except, при неудаче — не падать, а помечать карточку «требует ручной обработки» и отдавать администратору. Никогда не доверять, что LLM вернул валидную структуру.

**Дубли пациентов и сообщений.** Один пациент звонит с разных номеров или пишет в разные каналы. Дневной лимит и батчинг (Фаза 2) должны опираться на нормализованный номер телефона (единый формат +7XXXXXXXXXX). Нормализовать номер при каждом входе.

**Вебхуки приходят повторно.** Телефония может доставить один и тот же вебхук дважды. Идемпотентность по (номер + время звонка): повторный вебхук не создаёт второй лид и второе сообщение.

**Миграции БД.** SQLite сейчас, Postgres потом. Не хардкодить SQLite-специфику вразброс; вынести доступ к БД за тонкий слой, чтобы переезд не переписывал половину кода. Схему — через миграции, не ручным ALTER.

**Мультитенантность в каждом запросе (повтор из безопасности — потому что это и баг, и дыра).** Забыть фильтр по `clinic_id` хотя бы в одном запросе = показать чужие данные. Не полагаться на память: сделать хелпер доступа к данным, который ВСЕГДА требует `clinic_id`, и ходить в БД только через него.

**Идемпотентность подтверждения записи.** Ручной режим: тап «Подтвердить» шлёт пациенту финальное сообщение. Двойной тап не должен слать два. Флаг «уже подтверждено» на заявке.

**Порядок реализации при сомнении:** сначала корректность и изоляция данных, потом скорость. Если фича и безопасность конфликтуют в MVP — выбирай безопасность и оставляй `TODO` с пометкой.
